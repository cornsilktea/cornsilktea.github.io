# 교실 중계 서버(교사 노트북) 제작 프롬프트

작성 2026-11-28. **아직 만들지 않았다.** 아래 "프롬프트" 절을 새 작업에 그대로 붙여 넣어 시작한다.

## 왜 · 어떻게(요약)

- 지금: 기기 → 싱가포르 Realtime Database → 기기. 상대에게 닿기까지 약 150~200ms 가 기본으로 든다.
- 바꿀 것: 기기 → 교실 AP → 교사 노트북 → AP → 기기. 방·대전 자료만 노트북을 거치고, 로그인·통계·기록은 지금처럼 Firebase 로 간다.
- 화면(HTML·JS)은 지금처럼 GitHub Pages 에서 받는다. 노트북은 웹 서버가 아니라 **중계 서버**다.
- 연결은 **WebRTC DataChannel**. `https` 페이지에서 `ws://192.168.x.x` 로는 접속할 수 없고(혼합 콘텐츠 차단), 노트북 IP 용 인증서는 교실마다 IP 가 바뀌어 번거롭다. WebRTC 는 인증서·도메인·IP 입력이 필요 없다. 처음 연결할 때 주고받는 연결 정보만 Firebase 를 거친다.
- 게임 코드는 그대로 두고, **`firebase.database()` 와 같은 모양의 객체**를 만들어 끼운다.

## 프롬프트

```text
교사 노트북을 교실 중계 서버로 써서 실시간 대전의 통신 지연을 줄이는 기능을 만든다.
시작 전에 CLAUDE.md, docs/common/lan-relay-prompt.md(이 문서), docs/30.team-battle/30.team-battle-notes.md 2절,
docs/common/계정로그인.md, docs/common/random-match-prompt.md 를 읽는다.
한 번에 다 만들지 말고 아래 단계마다 멈추고 결과를 보고한 뒤 내 확인을 받는다.

[상황]
- 교사는 노트북을 들고 반을 옮겨 다니며, 그 반 와이파이에 연결한다. 학생 태블릿(갤럭시탭 S7 FE)도 같은 반 와이파이다.
- 지금은 모두 싱가포르의 Firebase Realtime Database 로 통신해 지연이 약 200ms 다.
- 목표는 통신 지연을 줄이는 것 하나다. 학생·교사가 쓰는 화면, 규칙, 로그인, 방 만들기·코드 입장·랜덤 매칭·관전·재접속·
  퍼즈, 계정 통계·최근 20매치·반별 순위 저장은 지금과 똑같이 동작해야 한다.

[구조]
1. 화면은 지금처럼 GitHub Pages(https)에서 받는다. 노트북은 중계만 한다.
2. 태블릿 ↔ 노트북은 WebRTC DataChannel(순서 보장·재전송 있음). 별 모양(모두 노트북에만 연결)이고 태블릿끼리는 연결하지 않는다.
   노트북 쪽은 Node(node-datachannel 권장, 안 되면 이유를 알리고 대안 제시). STUN·TURN 없이 같은 망 후보만 쓴다.
3. 중계 서버는 Realtime Database 흉내를 낸다. 메모리에 JSON 트리를 두고, 게임이 쓰는 것만 같은 의미로 구현한다:
   child/set/update(루트 "/" 여러 경로 포함)/remove/push, once, on·off(value, child_added, child_changed, child_removed),
   transaction(비교 후 교체, 충돌 시 다시 시도), onDisconnect().remove/cancel, .info/connected, .info/serverTimeOffset.
   쓴 기기에는 Firebase 처럼 자기 변경이 바로 보여야 한다. 빠진 기능이 없는지 ts/globals.d.ts 의 FirebaseRef 와
   게임·ts/common 의 실제 호출을 전부 찾아 표로 만든 뒤 시작한다.
4. 클라이언트는 공용 모듈(ts/common/lan-link.ts → common/lan-link.js)의 "경로 나누기 데이터베이스"다.
   - 노트북으로: 게임 방(예: teambattle/rooms, teambattle/parties), matchQueue/<게임>
   - Firebase 그대로: 로그인, users/*, classStats, gameRanks, records, portal(잠금·패치노트), 전체 통계(patchstats·modestats),
     perfDiag, usageDaily 등 나머지 전부
   같은 db 객체로 두 곳을 다 쓰는 코드가 있다(30번 MatchStats.path transaction, match-kit 의 ref("/") update).
   경로로 나눠 보내고, 한 update 에 양쪽 경로가 섞이면 나눠 보낸다.
5. db 객체를 거치지 않는 REST fetch 도 있다(30번 방 목록 shallow 읽기, 퍼즈 PATCH 등). 전부 찾아서
   방 자료를 읽고 쓰는 것은 같은 어댑터로 바꾼다. 통계·기록 저장 fetch 는 그대로 둔다.
6. 경기 종료 후 통계는 지금 코드 그대로 각 기기가 Firebase 에 직접 보낸다. 노트북은 통계를 대신 저장하지 않고
   서비스 계정 키 같은 비밀 값을 두지 않는다.

[접속 · 교사 화면]
7. 노트북에서 명령 한 번(npm run lan)이면 서버가 뜨고 http://localhost:<포트> 에 교사 화면이 열린다. macOS·Windows 모두.
   실행 중에는 노트북이 잠자기에 들지 않게 안내하거나 막는다.
8. 교사 화면에서 교사 계정으로 로그인하고 반을 고른 뒤 "교실 서버 켜기"를 누른다. Firebase 에 그 반의 서버 알림
   (켜짐·갱신 시각)을 쓰고, 끄거나 갱신이 끊기면 무효가 된다.
9. 연결 정보 교환(offer·answer)은 Firebase lan/<반>/signal/<uid> 로 한다. 학생은 자기 칸만, 교사 계정은 전부 읽고 쓴다.
   연결이 되면 지운다. 데이터베이스규칙.json 에 추가하고 게시하라고 알려 준다.
10. 학생은 학교 구글 계정(@dongma.sen.ms.kr)으로 로그인한 상태다. 연결되면 ID 토큰을 보내고, 서버는 서명·만료·프로젝트·
    도메인·email_verified 를 확인한 뒤에만 받아들인다. 교사 계정은 예외. 허용한 경로(4의 노트북 쪽)만 읽고 쓰게 한다.
11. 교사 화면 첫 화면은 접속한 학생 목록이다: 신호등, 이름(학번 포함), 핑(ms), 지금 있는 곳(목록/게임/방 코드), 접속 시각.
    - 핑: 2초마다 노트북↔태블릿 왕복, 최근 5개의 중간값
    - 초록 40ms 이하, 주황 41~100ms, 빨강 100ms 초과 또는 3초 넘게 응답 없음, 회색 화면 꺼짐·다른 앱
      (기준값은 한 곳의 상수로 두고 교실 실측 뒤 조정)
    - 연결 끊긴 학생은 바로 지우지 않고 "끊김"으로 1분 남긴다.
    - 전체 인원과 색별 인원 요약.
12. 학생 화면 한쪽에도 작은 신호등과 핑, "교실 서버" 표시를 둔다. 게임 HUD 를 가리지 않는다.

[어느 쪽으로 통신할지]
13. 반 링크(?c=1-1 …)이고 그 반의 서버 알림이 살아 있을 때만 교실 서버를 쓴다. 그 밖(대회서버·배포용·집)은 지금 그대로.
14. 알림은 있는데 연결에 실패하면 말없이 Firebase 로 넘기지 않는다(같은 방 코드가 서로 안 보이게 된다).
    "교실 서버에 연결 못함 · 다시 시도"를 보여 주고, 교사가 서버를 끄면 모두 Firebase 로 돌아간다.
15. 한 방 안의 모든 기기는 같은 통신 경로를 쓴다. 방 중간에 경로를 바꾸지 않는다.
16. 노트북 서버가 경기 중 꺼지면 "연결이 끊겼어요"를 보여 주고 시작 화면으로 돌린다. 다시 켜졌을 때의 처리(방 복구 여부)는 제안하고 물어본다.
17. 서버 시각은 Firebase 기준으로 보정한 값을 준다(통계의 시각·순서가 어긋나지 않게).

[단계]
0. 교실 확인 도구(가장 먼저, 이것이 실패하면 멈춘다): 노트북 서버 + 연결·핑만 재는 시험 페이지.
   내가 각 반을 돌며 태블릿 1대, 그다음 30대로 잰다. 확인할 것: AP 격리(기기 간 통신 차단), 노트북과 학생이 같은 망인지,
   UDP 차단, 노트북 방화벽, .local(mDNS) 후보 문제, 크롬의 "로컬 네트워크 접근" 권한 창(최신 크롬 정책을 검색해 확인).
   결과(평균·95%·최대 핑, 실패 원인)를 화면에 보여 주고 파일로 저장한다.
1. 어댑터와 서버. 노드 검사로 가짜 Firebase(tools/fbmock.js)와 같은 순서의 이벤트가 나는지 비교한다.
2. 교사 화면(접속 목록·핑)과 로그인 확인.
3. 30번 연결. 기존 &test·&sim 통과, 브라우저 여러 창 + 태블릿으로 방 만들기~통계 저장까지 확인.
4. 방이 있는 다른 대전 게임(room-kit·match-kit 을 쓰는 것부터)을 하나씩. 40번(동마의 숲)처럼 대전이 아니고 DB 규칙에
   기대는 자료는 제외.
5. (30번에서 효과를 잰 뒤, 내 확인을 받고) 교실 서버일 때만 전송 간격(NetState.NET_MS 143ms)과 원격 보간 지연
   (RemoteMotion.DELAY_MS 180ms)을 줄인다. Firebase 를 쓸 때 값은 그대로 둔다.
   이 두 값이 남아 있으면 통신이 빨라져도 체감 지연이 크게 남는다.

[코드 규칙]
- CLAUDE.md 의 객체지향·TypeScript·주석 규칙. 서버 코드는 tools/lan-server/ 에 두고 별도 tsconfig 를 쓴다.
- 교실 서버를 안 쓸 때의 동작·요청 수는 지금과 같아야 한다(서버 알림 확인은 잠금 확인에 얹는 방법을 먼저 검토).
- 저장소는 공개이므로 비밀 값·학생 정보 기록 파일을 커밋하지 않는다.
- 끝나면 docs/common/lan-relay-notes.md 에 구조·클래스 지도·검사 방법·수업 때 쓰는 순서를 적는다.

[보고]
단계마다: 한 것, 검사 결과, 확인하지 못한 것, 내가 할 일(규칙 게시, 교실 실측 등), 지연 전후 수치.
```

## 시작 전에 알아 둘 것

| 항목 | 내용 |
| --- | --- |
| 가장 큰 위험 | 학교 AP 가 기기끼리의 통신을 막아 두면(AP 격리) 이 방식은 안 된다. 그래서 0단계가 먼저다. 막혀 있으면 정보부에 해제를 요청하거나 휴대용 공유기를 쓰는 방법을 다시 정한다. |
| 인터넷 | 화면 받기·로그인·통계 저장 때문에 여전히 필요하다. |
| 랜덤 매칭 | 교실 서버를 쓰면 같은 서버에 연결한 학생끼리만 만난다(지금은 대기열이 모든 학생 공통). |
| 기대 효과 | 통신 왕복은 수~수십 ms 로 줄 것으로 보지만 30대가 붙은 교실 AP 에서는 재 봐야 안다. 30번은 전송 간격 143ms + 보간 180ms 가 따로 있어 5단계까지 해야 체감이 크게 달라진다. |
| 규칙 검증 | 노트북 서버는 `데이터베이스규칙.json` 의 값 검사를 하지 않는다. 학교 계정 확인과 경로 제한만 한다. 통계 저장은 Firebase 로 가므로 지금의 검사를 그대로 받는다. |

## 선택지(프롬프트에 가정으로 넣은 것)

- 접속 학생 목록은 **교사 노트북 화면**에 둔다. 학생 화면에도 목록이 필요하면 11·12번을 고친다.
- 핑 기준(40·100ms)은 임시값이다.
- 첫 대상 게임은 30번이다.
